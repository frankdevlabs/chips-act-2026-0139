## Assessment

Both re-probed live on 2026-07-20. The two verdicts differ: one is a transient host outage, the other is
a permanent, deliberate owner-side ban.

### `T1-04` — Council register ST 10094/2026 → **transient host outage, keep the URL**

- `https://data.consilium.europa.eu/doc/document/ST-10094-2026-INIT/en/pdf` → **HTTP 500, 0 bytes**, on
  three consecutive attempts; `/en/html` and the trailing-slash variant behave identically.
- **Control probe** (the decisive test): an *unrelated* document on the same endpoint,
  `.../ST-9000-2025-INIT/en/pdf`, also returns **HTTP 500**. The failure is therefore **not**
  document-specific — ST 10094/2026 has not moved, been withdrawn, or gone LIMITE.
- The host root `https://data.consilium.europa.eu/` still answers **200**, so it is the
  `/doc/document/*` service that is down, not DNS/network.
- `fetch_blocked_doc.py` reproduces it (curl tier HTTP 500 + 0 bytes; browser tier timeout, exit 2) —
  consistent with an upstream 500, which no WAF-solving tier can fix.
- No live substitute exists during the outage: `www.consilium.europa.eu` register search returns **403**
  (bot-block) for both the public-register search and the legacy `register/en/content/out` endpoint.
  This costs the repo nothing right now — the 3 June 2026 cover note is already committed at
  [`sources/council/ST-10094-2026_cover-note-proposal_2026-06-03.pdf`](../../sources/council/ST-10094-2026_cover-note-proposal_2026-06-03.pdf)
  (plus ADD 1), and no Council compromise text exists yet.

**Verdict: no URL change.** Wait and re-poll. What *is* worth fixing is the diagnosis: the run spent its
budget on the WAF fetcher for what was never a WAF problem. Record the outage signature and the
control-document test in the source's `notes` so the next run distinguishes "host is down" from
"document moved" in one probe.

### `T2-03` — INSIGHT EU MONITORING RSS → **retire the source**

Not an outage and not rate-limiting:

- Every feed path is blocked identically — `/feed/`, `/?feed=rss2`, `/feed/rss/`, `/comments/feed/`,
  a category feed, and even on-site search `/?s=chips+act` → **503**, ~22 kB Wordfence block page.
- The site **homepage returns 200** (479 kB) with the same client and UA, so the block is
  path/behaviour-scoped, not an IP ban on the whole host and not a UA problem.
- The block page states the reason explicitly: **"Block Reason: Accessed a banned URL"**, under a
  *"NOTICE TO USER OR BOT OPERATOR"* reading: *"If you operate a bot, crawler, AI system, or data
  aggregation service and wish to access or reuse our content, you must obtain a commercial licence.
  Unauthorised automated access may be logged and reported to hosting providers or network operators."*

That is a deliberate, stated policy decision by the site owner. The correct response is to **stop polling
it**, not to route around it with a browser tier — the repo does not evade an access ban, and this
tracker has no commercial licence. So T2-03 is removed rather than repaired.

Two consequences, both handled:

- **Existing citations stay.** `TIMELINE.md` (2026-06-09 Telecom Council row) and `STATUS.md` cite two
  IEU article URLs read before the ban. They remain valid citations of a source that was lawfully read;
  retiring the *watch* does not retract them.
- **The coverage gap is real but small.** T2-03's job was mirroring Council meeting outcomes while
  `consilium.europa.eu` bot-blocks. Replacement candidates were probed: Euractiv RSS **403**,
  Science|Business RSS **403**, Council press-release RSS **403**, `newsroom.consilium.europa.eu` is a
  multimedia SPA with no feed. **Eunews (`https://www.eunews.it/feed/`) answers 200** with a full RSS and
  demonstrably covers this file (03/06/2026 *"Chip, cloud e IA: Bruxelles lancia il pacchetto sulla
  sovranità tecnologica"*), so it is added as **T2-04** — a partial, secondary substitute, Italian-language,
  carrying the standard `keep_apart` warning (Italian coverage merges the two package halves, and CADA
  `2026/0138 (COD)` is out of scope).
